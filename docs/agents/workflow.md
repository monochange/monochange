# Workflow expectations

- Create a feature branch from `main`.
- Rebase onto `main` regularly while working so the branch does not fall behind and merge conflicts stay small.
- Always check the PR for merge conflicts before merging.
- Handle merge conflicts with a rebase onto `main` before merging, then rerun relevant validation.
- Add ready pull requests to the merge queue on `main`. The queue re-runs the required checks against `main` plus the batch and merges with squash to preserve linear history, so do not bypass the queue and do not push directly to `main`.
- When creating or updating a PR, manage failing checks proactively and use the scheduler to keep monitoring follow-up CI work until it is green.
- For complex or multi-step changes, start by creating or updating a plan under `docs/plans/active/` so the repo keeps a versioned execution record.
- For non-trivial behavior changes, start with a failing test.
- Implement the smallest change that makes the tests pass.
- After making changes, run `fix:all` so formatting and clippy autofixes are applied before final validation.
- Update docs, READMEs, fixtures, changeset examples, and templates when behavior changes.
- Always include a `.changeset/*.md` file when changing code in any published crate. Choose a bump that matches the behavior and API: compatible additions require `minor`, breaking changes require `major`, and fixes that preserve the API use `patch`. A new published package or crate requires a first `major` changeset. Add or adjust notes for every affected package.
- While working, run `monochange step affected-packages --verify --changed-paths <path> --changed-paths <another-path>` to check package coverage for explicit paths. Pass every changed file relative to the repo root, including added or edited changeset files. Each `--changed-paths` flag accepts exactly one value: repeat the flag rather than passing several whitespace-separated arguments or combining paths with commas. Explicit-path verification checks coverage; it does not compare APIs or verify bump alignment.
- After committing code and changesets, run `monochange step affected-packages --from origin/main --verify` before opening or updating the PR. This comparison-based verification matches CI and checks release intent against API changes as well as package coverage. Resolve missing coverage and bump mismatches, commit corrections, and rerun it.
- Changes limited to configured `ignored_paths` can pass without a changeset. Only Ifiok Jr. may decide that a change needs no changeset and apply `no-changeset-required`; agents must never add that label.
- Choose changeset streams by audience, independently of package type. Keep operator-only deployment and CI notes in the developer stream, including for applications. Product notes describe visible behavior. For CLI changes include before/after command invocations; for library changes include before/after type signatures or usage examples; for config changes include before/after TOML snippets; for breaking changes open with a blockquote and give a migration path. See [Changeset quality](changeset-quality.md) for the full standard.
- Use package-centric, granular changesets. Review existing `.changeset/*.md` files before creating a new one so you can decide whether the right lifecycle action is create, update, replace, or remove. Distinct features should get distinct changesets even when they land in the same package; only expand an existing changeset when the new work is clearly the same feature growing in scope.
- Err on the side of creating a new changeset. It is easier to consolidate related notes later than to split an overly broad changeset after the fact.
- Breaking changes must always get their own dedicated changeset with a migration path instead of being bundled into a broader feature note.
- Follow [Changeset generation](changeset-generation.md) when deciding changeset lifecycle actions, artifact-aware framing, and how granular to make release notes for libraries, CLI tools, and applications.
- When adding or changing configuration options in any crate, update the annotations in `monochange.toml` to reflect the new option, its defaults, available values, and purpose. Use the existing comment style as a guide. Where possible, use mdt shared blocks in `.templates/` so the same documentation propagates to the guide, README, and config file.
- Run the full local validation suite before opening a PR.
- Patch coverage for executable changed lines must be 100% before opening or merging a PR. Treat anything lower as a blocker and add or adjust tests until the patch gate passes.
- During review, explicitly check architecture boundaries for touched code: core defines contracts, adapter crates own implementation details, and `crates/monochange` only orchestrates.
- If touched code adds provider/ecosystem-specific validation or mutation logic outside an adapter crate, either move it behind adapter dispatch or document why that exception is unavoidable.
- For refactors that move implementation details across crate boundaries, add or update realistic fixtures and integration tests so patch coverage for executable changed lines stays at 100%.
