## Definition of done

Both the landing/GitHub connection website and projects application have explicit, truthful Leptoskit crate/configuration ownership. The pinned upstream CLI builds their real artifacts; its application/workspace schemas validate their declarations. CI and the deployment image use those builds instead of cargo-leptos. A running image serves both surfaces, their real CSS/JS/WASM and lazy routes, while preserving one login authority, existing endpoints and secure cookie behavior. Deployment configuration is reviewable and tested; no production cutover or infrastructure mutation is part of this development task.

## Grounding and constraints

- Current web configuration is app/leptoskit.toml, but CI and Docker still use cargo-leptos. monochange_app owns both server and browser entry points; monochange_projects owns product pages but has no independent browser entry point. Native and extension already use Leptoskit and shared sessions.
- Upstream at the captured commit provides application schema version 0 and workspace format version 1. Application roles are applications.<id>.kind in leptoskit.workspace.toml. Backend package selection is app.name plus build.backend; browser package selection is build.client_package. Do not invent a server_package or generic crates table.
- Source references: docs/src/guide/03-configuration.md, 24-deploying.md, 33-workspaces.md; crates/leptoskit_config/src/lib.rs and workspace.rs; crates/leptoskit_cli/src/{build,server,deploy,workspace}.rs. A source archive is retained in the parent ignored local artifacts at leptoskit-fa3d29f8e8c837b19f92f1e9a95f699803543767/.
- The workspace scaffold does not supply shared sign-in. Preserve monochange's existing authority rather than assuming bindings grant user identity. Preserve the host-only secure cookie, bearer priority, Origin rules, PKCE handoff, revocation and Class B hosted API authentication.
- Preserve the current DigitalOcean container/SQLite/Monosecret runtime and public URLs. Upstream managed infra requires Postgres; adopting that would be a separate database and cloud migration. SQLite-capable deployment exporters are the relevant path here.
- Upstream generated Dockerfiles default to a registry install of leptoskit_cli. That does not establish the reviewed Git provenance. Test and correct the source-install wiring explicitly.
- Only one coherent implementation unit at a time, isolated children, commands and real output required. Start with roughly 20-30 manifest/config/pipeline/docs files; scope any frontend entry-point extraction separately after the toolchain probe. Do not widen a failing task silently.
