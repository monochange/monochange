## Unit 2+3 scope (2026-11-10)

The former units 2 and 3 are implemented as one coherent release change, not a widening of unit 1: giving the browser entry points real crate ownership without simultaneously moving CSS/loader production, CI, and the deployment image onto those builds would deploy a site whose assets the leptoskit pipeline never produces. Chosen architecture, verified against the SDK source at the pinned revision:

- Two browser entry points and bundles, one same-origin backend/session authority. The website browser entry keeps landing, login, account, consent (GitHub connection), docs/changelog/pricing/install, and the repositories dashboard at `/dashboard`. monochange_projects gets its own cdylib/hydrate entry and owns the product root: `/projects` routes, `/p/:organization/:project` public feedback portal views, and product hydration. The historical `/dashboard/*` product paths keep their existing permanent server-side redirects to `/projects/*`.
- One backend process composes both SSR route sets. `leptos_axum`'s `leptos_routes_with_context` registers server-function API routes from `server_fn_paths()` and page listings together, so the composition calls it exactly once with the merged listings of both route trees and a server-side dispatcher that renders the matching frontend router (and its document shell with that frontend's hydration scripts, stylesheet, and split manifest) from the request path. Routers are never merged; `/api` is registered once.
- leptos 0.9's `HydrationScripts` caches the entry file names and split manifest in process-global `OnceLock`s keyed to the first caller, so one process cannot serve two output names through it. The composition therefore renders per-frontend hydration scripts explicitly (modulepreload, wasm preload, and leptos 0.9's hydration script with per-frontend paths, plus the `WasmSplitManifest` context for lazy-chunk preloads), keeping the emitted markup and behavior identical to upstream for each frontend.
- Each frontend builds through its own real `leptoskit.toml` (website at `app/leptoskit.toml`, projects at a config-only `app/projects/leptoskit.toml`, supported by Cargo workspace parent discovery). Both truthfully name the same backend package (`app.name = "monochange_app"`, which owns the server binary) while selecting distinct browser packages via `build.client_package`. `[[plugins]]` on both web configs runs a TypeScript tooling plugin on the documented JSON stdin/stdout process protocol (`crates/leptoskit_plugin/src/process.rs`, protocol 1): its `after_build` hook — which upstream runs before release precompression — minifies the wasm-split loader with the existing guarded `minify-split-loader.ts` implementation, compiles the shared Tailwind input to `pkg/<output_name>.css`, and places the frontend's pkg output under its `pkg/<namespace>/` so both builds assemble one coherent site root.
- Root `leptoskit.workspace.toml` (format_version 1) declares website (landing), projects web (product), native mobile (product), and extension (product) with their real paths. No invented bindings, environment names, or runtime claims; `workspace check` is configuration-only.
- CI and the Docker image stop using cargo-leptos entirely. The image builds and verifies the same Git-pinned CLI via `[workspace.metadata.bin]`, keeps pinned node/esbuild/tailwind/binaryen, and preserves Monosecret privilege drop, no-new-privileges, SQLite volume, secret mounts, `/health`, and Class B APIs. `leptoskit generate deploy` remains refused for this workspace (path deps outside `app/`); the hand-maintained Dockerfile documents that exporter limitation explicitly and is not presented as generated output.
- The website browser entry drops the signed-in projects route tree and the dynamic navigation/shell switching; cross-frontend links render with `target="_self"` so the router's anchor interception lets the browser load the correct entry document. Lazy navigation inside each frontend is unchanged.
- The split removes and moves public items of the workspace-internal crates (the website's projects route re-exports, `monochange_app::{markdown,projects}` re-exports, `ErrorTemplate` now re-exported from `monochange_projects::error`), so the changeset carries a major bump for `monochange_app` per API classification.

## Repair unit 1 results (2026-11-11): dedicated projects entry and repaired comparisons

The dual candidate kept the product route tree in `monochange_projects`, which the website browser also links for shared components — so the website bundle carried the four product-route split **exports with no matching imports**. wasm-split pairs imports with exports to move code into chunks; unpaired exports stay in the main module, and wasm-dis on the candidate's `site/monochange_app_bg.wasm` showed exactly four live `__wasm_split_00__{organization,portal,project,feedback_console}_route_view_*` exports retaining ~824 KiB raw (335 KiB gzip) of unreachable product code. ## Publisher exclusive-ownership unit (2026-11-13)

Two premises failed the recovery/concurrency gate before this unit:

1. **Prefix sweeping is safe.** The asset-lifecycle publisher deleted every `.site-staging-*` and `.site-previous-*` beside the site root before staging. A publication interrupted between its two renames leaves its only last-good tree in `.site-previous-*`, so the next run destroyed it. A concurrent run's staging and previous trees were deleted as well. A post-commit `rm` failure also reported a failed publication after the output had already changed.
2. **Atomic renames alone coordinate a shared recovery slot.** The rejected proposal c6cf7cbbc5531ae66c2bef641fa3e9c4d5c44266 removed the sweeps and used one fixed `.<site>.publish-previous` slot without exclusion. The primary tested that premise directly with two owned Node processes, filesystem barriers, and a single injected promotion I/O failure. A committed and paused before retirement. B retired A's original backup and moved committed A into the shared slot. A then resumed, deleted B's copy, and exited 0. B's rollback failed with ENOENT. The end state was no site and no recovery slot, while B's error still claimed a retained tree (primary's ignored `.monochange/local/review/publisher-concurrency/result.json`). Its 20 focused tests passed regardless.

**The contract now (exclusive ownership).** One publisher owns a destination from staging through promotion and retirement, through the lease directory `.<site>.publish-lease` beside the site root.

- **Acquisition.** The publisher writes `owner-<token>.json` (the random 16-hex token is its name; pid, host, and start time are inside) into a claim directory only it names, then renames the claim to the lease. The rename fails while a lease exists. A lease always holds its record, so it is never an empty directory a rename could replace.
- **State.** All transient state lives inside the lease (`staging/`, `previous/`). Nothing beside the site root is ever removed by name pattern.
- **Held lease.** A held lease fails every other publication before it changes anything. The error names the owner, the trees the lease retains, and the recovery command.
- **Swap.** Promotion remains the documented two-rename swap (`site` → `<lease>/previous`, `<lease>/staging` → `site`), with its honest absence window. Production copies the finished tree into the image before serving, so no hot-deployment platform is involved.
- **Rollback failure.** A failed second rename rolls back. If the rollback also fails, the last-good tree stays in `<lease>/previous` under the still-held lease (`RecoveryRequired`), and only verified paths are named.
- **Release.** Release renames the lease to `.<site>.publish-retired-<token>` and removes it. A post-commit removal failure is a warning with a retained directory that no later run touches, never a failed publication.
- **Ownership proof.** Ownership is checked before the swap and before release. A lease that lost its owner record is left untouched.
- **Recovery.** Recovery is explicit and never automatic: `--site-root <dir> --recover-abandoned-lease <token>`, run after the operator confirms the owner is gone. It adopts the lease by renaming the owner record, as a compare-and-swap. It then restores `previous/` to an absent site root, or sets it aside as `.<site>.publish-retained-<token>` and never deletes it. Finally it releases the lease, discarding only the never-published staging tree.

Limits and remaining gates, recorded honestly:

- **Recovery is never automatic.** An interrupted publication — including Ctrl-C during compression — makes the next publication of that site fail closed until the operator confirms the owner is gone and runs the named recovery command. `build:web` does not pre-check the lease before its multi-minute builds (devenv.nix was out of scope).
- **Docker cache mount.** Docker's `app/target` is a BuildKit cache mount. A cancelled image build that leaves a lease makes the next build on that builder fail closed. The mount holds no deployed state; recover there, or drop that cache mount deliberately.
- **Cooperating publishers only.** The design assumes cooperating publishers of this version. An older-format publisher running concurrently is not excluded, and its `.site-staging-*`/`.site-previous-*` leftovers are never touched (remove them by hand).
- **Tiny-window leftovers.** A kill inside the microsecond window between writing a claim and renaming it leaves a harmless `.<site>.publish-claim-<token>` directory. A kill between the release rename and its removal leaves a `.<site>.publish-retired-<token>` directory. Neither is ever consulted; both are removed by hand.
- **Operator error.** Recovering a live owner's lease is operator error. The live owner then proves it no longer owns the lease and leaves it untouched, but exclusivity was broken by the operator.
- **Coverage.** Inherited cumulative Rust patch coverage remains 823/826 (`app/crates/monochange_projects/src/components/navbar.rs:115,116,121`). It is left red as separate next work; this TypeScript-only unit adds no exclusions and did not rerun Rust coverage.
- **Release gates still open.** Production rollout/rollback audit, data-upgrade review, and final release preparation. No release is live and the migration is not finished.

### Deployment-helper audit for the next rollout unit (read-only, unchanged here)

1. `monochange-deploy.sh` takes no lock and takes no backup; only `ci-deploy.sh` does both (`flock` on `/opt/monochange/.deployment.lock`, `monochange-sqlite-backup` before restart). A manual deployment runs entirely without them; the docs instruct but nothing enforces.
2.
