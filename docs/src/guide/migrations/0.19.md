# Upgrading to 0.19

Version 0.19 makes hosted release commits refresh the release pull request, adds `yarn.lock` support, and changes two library APIs. Repositories that don't use the hosted backend or the Rust crates directly need no changes.

Each section states who is affected, what changed, and the exact update step. The complete change list for this release lives in [changelog.md](../../../changelog.md).

## Release step commands share one release branch

_Affects: workflows that run `monochange step open-release-request` or `monochange step commit-release` and rely on the old branch name._

Built-in step commands used to name the release branch after the step, so `monochange step open-release-request` opened `<branch_prefix>/step-open-release-request`. Every `step <name>` command now uses `<branch_prefix>/release`, the same branch a `[cli.release]` workflow uses.

Update steps:

- Close any open release pull request from the old branch and delete the branch. The next run opens the pull request from `<branch_prefix>/release`.
- Update branch protection rules or workflow filters that name the old branch.

## Hosted release settings follow the step first

_Affects: workflows that use the hosted backend with `MONOCHANGE_HOSTED_URL` and a configured `hosted_url`, or that pass `--hosted-auth`._

Hosted settings now resolve in this order: the step input (flag or workflow `inputs`), then `MONOCHANGE_HOSTED_URL` (for the URL only), then the step configuration, then the defaults (`https://monochange.dev` and an OIDC audience derived from its host). Previously a configured `hosted_url` won over `MONOCHANGE_HOSTED_URL`, and `--hosted-url` and `--oidc-audience` were ignored on step commands. An unknown `hosted_auth` value in workflow `inputs` now fails instead of silently falling back to the configured mode.

Update steps:

- If you set `MONOCHANGE_HOSTED_URL` and `hosted_url` to different deployments, remove the one you don't want.
- Workflows that set `GITHUB_HEAD_REF` to the release branch so hosted commits land there can drop that override; hosted `CommitRelease` now always targets the release branch.

## Library APIs

_Affects: Rust code that depends on `monochange_core` or `monochange_npm`._

`monochange_core::HostedCommitRequest` gains `base_branch: Option<String>`, the branch the release was prepared from. The monochange app uses it to tell a stale run from a refresh. Struct literals must add the field:

```rust
// before
let request = HostedCommitRequest { owner, repository, branch, base_commit, /* … */ };

// after
let request = HostedCommitRequest {
	owner,
	repository,
	branch,
	base_commit,
	base_branch: Some("main".to_owned()),
	/* … */
};
```

Serialized requests omit `base_branch` when it is `None`, so older payloads still deserialize.

`monochange_npm::NpmVersionedFileKind` gains a `YarnLock` variant for `yarn.lock` support. Exhaustive matches must handle it:

```rust
match kind {
	NpmVersionedFileKind::YarnLock => { /* new */ }
	// existing arms…
}
```
