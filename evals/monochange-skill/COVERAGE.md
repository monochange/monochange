# Coverage: monochange skill evaluation matrix

A prioritized map of every decision surface the monochange CLI exposes, what the existing eight scenarios already cover, where the gaps are, and which grading style each gap needs. Written against the built binary at `target/debug/monochange` (surface enumerated from `--help` on every command) and the crates under `crates/`, so the config keys and commands named here are the ones the binary actually accepts.

## The two grading styles

Every row in the matrix below is either:

- **agent** — costs money, tests judgment. Reserve it for tasks where a human-like decision is the point: choosing a severity, choosing between files, deciding to stop and ask, refusing to do something destructive.
- **contract** — `"agent": false` in the scenario schema. Costs nothing, runs in CI, and pins deterministic behavior with `command` checks against the real binary. Everything mechanical belongs here, including behaviors the skill merely documents (`"agent": false` scenarios already prove the pattern: see `cli-self-sufficiency`).

The split follows the lesson recorded in the Pina suite's FINDINGS: grading a stochastic agent run tells you nothing about a deterministic contract, and a model that already knows the answer will not go looking, so "the agent should find X" is a property of the toolkit, not of the run.

## Current state

Eight scenarios over six fixtures. Seven are agent scenarios, one is a contract scenario:

| Scenario                       | Style    | Fixture          | What it owns                                                                                                          |
| ------------------------------ | -------- | ---------------- | --------------------------------------------------------------------------------------------------------------------- |
| `adopt-mixed-monorepo`         | agent    | `mixed-monorepo` | Adoption for cargo + npm, quoted scoped TOML keys, one group over all packages, config survives the release-time load |
| `breaking-change-changeset`    | agent    | `npm-monorepo`   | Severity judgment (major), scoped id quoting in changeset frontmatter, group 2.3.1 → 3.0.0                            |
| `cli-self-sufficiency`         | contract | `rust-workspace` | `monochange skill` list / read / install / `--force` / unknown-topic exit codes                                       |
| `dependency-propagation`       | agent    | `rust-workspace` | Minor on a library, propagated bump to a dependent, grouped-vs-propagated distinctness                                |
| `gitignore-release-state`      | agent    | `rust-workspace` | Only `.monochange/local/` may be ignored; release records stay tracked                                                |
| `python-release-version-write` | agent    | `python-uv`      | Python adoption, explicit `versioned_files` with `fields = ["version"]`, `prepare` actually writes both manifests     |
| `release-without-publishing`   | agent    | `npm-monorepo`   | Prepare writes the group to 2.4.0, changelogs written, nothing published, tagged, or pushed                           |
| `stream-split-changesets`      | agent    | `npm-monorepo`   | One stream per file, `step validate` does not catch cross-stream, `monochange notes --output/--target` selection      |

Fixture inventory: `mixed-monorepo`, `npm-monorepo`, `rust-workspace`, `python-uv`, `go-modules` (no scenario), `dart-workspace` (no scenario). Deno has neither fixture nor scenario. `DESIGN.md` also promises an `empty-workspace` fixture that does not exist yet.

Priority legend: **P0** = next batch, protects surfaces that already broke or are completely dark; **P1** = core contract, high regression value; **P2** = valuable, currently stable; **P3** = marginal.

## Verify before writing scenarios

Claims the matrix makes that were not fully reproduced and must be triaged first. Each is cheap to check against `target/debug/monochange`.

1. **`monochange create --dry-run` writes the changeset file.** Verified twice in a clean workdir: after `create --dry-run --package acme-core ...`, `.changeset/<timestamp>-acme-core.md` exists on disk while the output says `wrote change file`. Either a defect (dry-run must not mutate) or intended; the scenario asserts whichever behavior is decided, and this is exactly the "dry-run discipline" the skill teaches.
2. **Go tag naming and the `require` rewrite.** FINDINGS records Go planning works with tagged initial versions but `changed_files` stays empty. Before writing the Go scenario: confirm the exact tag format the Go adapter resolves (`core/v1.2.0` vs `v1.2.0`) via `step release-record`/`next` on a tagged fixture, and re-test whether the `require` line rewrite landed.
3. **`lockfile_commands` replacement semantics.** The claim "replaces the built-in rewrite" needs one experiment: configure a command that writes a sentinel into `pnpm-lock.yaml` and confirm the built-in writer did not also run.
4. **Provenance scope.** `registry_native_provenance` gates are adapter-level (`crates/monochange_publish/src/lib.rs:3085`); confirm by config experiment which ecosystems reject `require_registry_provenance = true` before pinning the error.
5. **`init --provider` provider set.** `init --help` says `github, gitlab,
   gitea`; config accepts `forgejo` too. Confirm `init --provider forgejo` errors (or works) before pinning.
6. **Deno publish target naming.** The publish crate references JSR provenance and placeholder `deno.json` writes; confirm the readiness surface for a deno package labels the registry as JSR before asserting it in checks.

## Not worth testing

Surfaces examined and deliberately left out, with the reason in one line:

- **`monochange command`** (interactive dashboard) — requires a TTY; the same config edits are graded deterministically through files.
- **`--progress-format`** — pure tracing-formatter passthrough with no decision or artifact behind it.
- **`monochange help <cmd>`** deep help — clap passthrough; the `skill` advertisement already pins the one help string agents depend on.
- **`step comment-released-issues`, `open-release-request`, `publish-release`, `plan-publish-rate-limits`** — need live hosted-provider state, and provider release creation is a human-maintainer-only operation per AGENTS.md authority limits; offline value is limited to config-error checks folded into the `release-history` batch.
- **`mcp` end-to-end** — the twelve tools wrap the same engine as graded CLI commands, so a JSON-RPC harness would test `rmcp` transport, not monochange decisions; pin the inventory only.
- **`change classify` / `changeset validate --api` / `analyze` / `api diff` verdicts** — FINDINGS established the analyzer verdict depends on the fixture's installed toolchain (same diff: `minor` with the workspace compiler, `patch` without), so premising a check on a verdict grades the machine; at most pin output shape.
- **`migrate audit`** — read-only report over other tools' configs; no monochange decision in it (P3 if ever).
- **`migrate release-records`** — schema migration for records the suite does not yet create; revisit after `release-history` exists.
- **`lint new`** — scaffolds a rule inside an ecosystem crate: contributor workflow, not release-planning judgment.
- **`next` vs `next-versions`** — verified identical (same `DisplayVersions` step); one assertion inside the format-contract scenario is enough.
- **Publish order vs dependency order against real registries** — honest coverage needs a registry fake the harness does not have; a fake half-test would assert the mock, not monochange.
