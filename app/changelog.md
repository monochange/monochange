# What's new on monochange.dev

User-facing website release notes generated by monochange.

## 0.3.1

### New

#### Fair use limits for the monochange.dev API

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #807](https://github.com/monochange/monochange/pull/807)

monochange.dev now limits how quickly one client can call its API, so a single script can't slow the site down for everyone else. Normal browsing never comes close to the limit. Signed-in users get five times the allowance of anonymous visitors.

If you do hit the limit, the site tells you how many seconds to wait before trying again. Scripts that read the public task API get a `429 Too Many Requests` response with a `Retry-After` header, and every API response reports how many requests remain.

#### Search, filter, and page through your repositories

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #804](https://github.com/monochange/monochange/pull/804)

The dashboard no longer lists every connected repository at once. Each account folds open to its repositories, 20 to a page, in a list that scrolls inside the window. Search by repository name, or pick one account, to narrow every list; the search stays in the address so you can reload or share the filtered view. An organisation's page gets the same search and pages, and the repository checkboxes when you create or edit a project can be filtered by name.

The "Free" label beside each repository is gone; each row now shows whether the repository is public or private.

### Improved

- **Set up bot release pull requests without a token.** The GitHub App guide now walks through using monochange.dev to create release commits and release pull requests: why the app replaces `GITHUB_TOKEN` and personal access tokens, what to approve when installing the app, the `monochange.toml` change, and a complete GitHub Actions job that only needs `id-token: write`. It no longer says hosted releases need a separate rollout, and it explains that monochange.dev does not issue per-user `MONOCHANGE_TOKEN` values, so hosted release commits run from GitHub Actions. _Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #806](https://github.com/monochange/monochange/pull/806)

## 0.3.0

### New

#### Hand accepted feedback to a coding agent

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #798](https://github.com/monochange/monochange/pull/798)

Maintainers can now choose **Build with an agent** on accepted feedback that has a GitHub issue. The agent runs in the repository's own GitHub Actions, so code and model keys stay there, and it opens a draft pull request for review. The item shows as "in development" on the portal, then moves to review, merged, and shipped as the pull request does.

To use it, add the agent workflow from the new "Build accepted feedback with an agent" guide to the repository first.

#### Follow feedback from pull request to release

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #788](https://github.com/monochange/monochange/pull/788)

Accepted feedback now moves on its own as the work happens on GitHub. When a pull request that fixes the feedback's issue is opened, the item shows as in review. When it merges, it shows as done. When a release is published, it shows as shipped, with a link to the release notes. Everyone who shared, voted on, or discussed the item gets each update on the project's feedback portal, and maintainers no longer update the status by hand.

If you registered your own GitHub App for monochange, add the **Release** event to its webhook subscriptions.

- **Connect repositories from your monochange dashboard.** Sign in and install the monochange GitHub App from the dashboard to choose the personal or organization repositories you want to connect. monochange keeps the connection available when you return to add or change repositories later. _Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #782](https://github.com/monochange/monochange/pull/782)
- **Organise repositories into projects.** Your workspace now groups connected repositories by organisation. Open an organisation to see its repositories and create a project that brings several of them together under one name. You can rename a project, change its repositories, or delete it at any time. A project keeps its repositories if the GitHub App is uninstalled and reinstalled, and shows them as disconnected in between. _Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #785](https://github.com/monochange/monochange/pull/785)

#### Sign in with GitHub to share and vote on a project's feedback

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #798](https://github.com/monochange/monochange/pull/798)

Anyone can still read a project's feedback portal. To share a bug or an idea, vote, or join a discussion, visitors now sign in with GitHub, and they come straight back to the portal afterwards. Each account counts once, so votes reflect real people. Visitors' GitHub names are never shown on the portal or to maintainers.

The portal also has a new look. The project's page opens with counts of what is under review, planned, in progress, and shipped. The roadmap is a board of cards with clearer voting, and each thing you shared shows a tracker from "shared" to "shipped".

If you shared feedback before this change without signing in, it stays on the roadmap with its votes, but it won't appear under "Yours".

#### Collect feedback from the people who use your projects

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #786](https://github.com/monochange/monochange/pull/786)

Every project now has a public feedback portal at `/p/{organisation}/{project}`. Visitors can report a bug or suggest an idea in a Markdown editor with formatting buttons and a preview. Before they send, they see similar requests they could vote for instead. They can then follow everything they shared on the same page, answer follow-up questions, and read status updates until it ships.

Maintainers triage it all in the project's feedback console. There they accept, decline, or fold duplicates, rewrite public titles, reply, and open a GitHub issue for accepted work in any of the project's repositories. If any of a project's repositories is private, the portal hides internal paths and addresses from public view; secrets and personal details are hidden on every project.

#### Share accepted work with contributors (experimental)

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #801](https://github.com/monochange/monochange/pull/801)

Maintainers of public projects can turn on **Shared compute** in the feedback console and share an accepted item as a task: a title, acceptance criteria, the paths it may change, and the command that proves it. Contributors will run these tasks with their own coding agents. Every task is screened before it lists, so a task can't ask for anything on a contributor's machine, and anyone can read the open tasks to see exactly what was asked.

The command that runs tasks on a contributor's machine comes next. See the new "Share tasks with contributors" guide.

- **Faster pages and smaller downloads on monochange.dev.** The website now loads its interactivity in per-route pieces instead of one large download: the home page no longer fetches the code behind the dashboard, book, changelog, pricing, or feedback portal, and each of those pages fetches its code only when you open it. Transfers are compressed and reusable assets are cached with cheap revalidation, so returning visits re-download almost nothing and pages after the first feel immediate, especially on slower connections. _Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #796](https://github.com/monochange/monochange/pull/796)

### Improved

- **Keep hosted release pull requests up to date on every push.** Repositories that publish releases through monochange.dev get a refreshed release pull request after each push to the base branch. Previously only the first push opened the release pull request, and later pushes failed until it was merged. No action is needed beyond using a monochange CLI that includes this release. _Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #789](https://github.com/monochange/monochange/pull/789)

#### Fail hosted release commits that GitHub does not verify

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #763](https://github.com/monochange/monochange/pull/763)

The monochange app now stops a hosted release when GitHub does not verify the release commit, and leaves the release branch where it was. Before this fix, the release branch moved to the unverified commit anyway, so a repository with required signed commits only learned of the problem when branch protection blocked the merge. The error names the commit and the reason GitHub gave.

This changes no settings or configuration. Repositories with verified-commit requirements now get an explicit failure instead of a misleading success.

- **Progress output docs explain ASCII result symbols.** The progress output reference and the CLI steps guide on monochange.dev now say that `--progress-format ascii` also keeps command results on stdout within ASCII. Anyone reading results in a terminal or log viewer without Unicode support can now see which symbols to expect. _Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #794](https://github.com/monochange/monochange/pull/794)

### New

The configuration guide covers the new `publish.flow` option for npm packages, so you can read how to hold each release for maintainer approval with 2FA before it becomes installable. _Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #764](https://github.com/monochange/monochange/pull/764)

#### Connect repositories from your workspace

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #761](https://github.com/monochange/monochange/pull/761)

When repository connection is available, open its GitHub installation page from your dashboard. Choose all repositories or selected repositories on GitHub, then return to the dashboard. If connection is unavailable, the workspace explains that setup is still needed instead of implying that signing in connected your repositories.

First-time connections now appear even when you connect on GitHub before signing in to the website. Your workspace follows repository selection changes, paused connections and removals for each connected account. Connecting repositories does not enable hosted release automation.

### Improved

#### Keep your workspace signed in after GitHub login

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #761](https://github.com/monochange/monochange/pull/761)

The dashboard and navigation now recognize a completed GitHub sign-in, including after a reload. Signing out clears the browser session and returns you to the public website. Failed or expired sign-ins ask you to try again without creating a session.

Connected public and private repositories are limited to your account. Organization repositories are shown to the installer only while GitHub confirms they remain an active organization owner.

## 0.2.0

### Changed

#### Use the website's book address for new documentation links

_Owner:_ [@ifiokjr](https://github.com/ifiokjr) · _Review:_ [PR #752](https://github.com/monochange/monochange/pull/752)

> The website's documentation destination is now `/book` on `monochange.dev`.

Point new documentation links and bookmarks to `https://monochange.dev/book`. Existing `/docs` links redirect to the matching chapter. The standalone book remains available, with a link back to the website.

For example, update a documentation link in Markdown:

```markdown
[Read the book](https://monochange.dev/book)
```
